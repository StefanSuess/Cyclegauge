# Installing and using Cyclegauge for Kiro IDE

> Extension ID: `StefanSuess.cyclegauge`; commands and settings use the `cyclegauge.*` prefix.

## Install the published beta or build a development VSIX

The published beta is available on [Open VSX](https://open-vsx.org/extension/StefanSuess/cyclegauge) and under [GitHub Releases](https://github.com/StefanSuess/Cyclegauge/releases). To test unreleased changes, build a VSIX from a checkout (Node.js 24.13 or newer and pnpm):

```sh
pnpm install --frozen-lockfile
pnpm package:vsix
```

Then run **Extensions: Install from VSIX...** in Kiro and select the file in `dist/`. Reload the window if Kiro asks, then open **Cyclegauge: Show Account Credits** (command ID `cyclegauge.showUsage`) or click the status-bar item. This command only opens the local billing view.

Settings: `cyclegauge.sourceRoot`, `cyclegauge.storageRoot`, and `cyclegauge.sourceTimezone`. Blank settings use the platform's default IDE/app-owned locations and device timezone. `cyclegauge.sourceRoot` exists for testing and demos with synthetic logs; normal use leaves it blank. Offset-free historical log timestamps may be ambiguous if the device timezone changed. Stale or unavailable values are labeled. CLI and Crew session metering and add-on balance aggregation are not read.

| Setting | Scope | Default | Purpose |
| --- | --- | --- | --- |
| `cyclegauge.sourceRoot` | machine | empty | Synthetic logs for tests and demos; empty reads Kiro's standard data folder |
| `cyclegauge.storageRoot` | machine | empty | Private Cyclegauge storage folder; empty uses the editor's per-extension storage |
| `cyclegauge.sourceTimezone` | machine | empty | IANA timezone for offset-free log timestamps; empty uses the device timezone |
| `cyclegauge.auditReminderDays` | user | 30 | Days between workspace audit reminders; 0 turns them off |
| `cyclegauge.auditAutomatically` | user | `off` | `onOpen`: silently re-run an audit older than one day when the workspace opens; `onOpenAndChanges`: also re-check when matching files appear |
| `cyclegauge.supportPrompts` | user | on | Occasionally ask whether you'd rate or support Cyclegauge; off stops it |
| `cyclegauge.budgetWarnings` | user | on | Budget notices inside Kiro (see Budget warnings); off stops them |
| `cyclegauge.sessionHints` | user | on | Session hints (macOS observed, Windows and Linux enabled, not yet verified natively): context reminder and model hint from your newest Kiro session (see Session hints); off stops all reading |
| `cyclegauge.budgetWarningPercent` | user | 80 | Share of the reported credit limit (0 to 100) at which the early notice appears; 0 turns only that notice off |

## Getting started

After installation, new users inside Kiro get a short walkthrough, **Get started with Cyclegauge**, opened once. It shows where your Kiro credits are, offers the workspace check right away (it needs no usage history), points to the budget warning settings, explains the session hints (and how to turn them off) and says when the forecast appears: a provisional estimate after about 2 days and 3 updates, a regular forecast after 7 days and 8 updates. Open it any time with **Cyclegauge: Get Started** (command ID `cyclegauge.gettingStarted`). Users who already had Cyclegauge (any earlier Cyclegauge state) and users who turned `cyclegauge.supportPrompts` off are not shown it, and it never opens outside Kiro or in extension tests. Only one flag is stored (see [privacy and storage](privacy-and-storage.md)). Walkthrough support is not yet verified in native Kiro; if the editor cannot open it, nothing happens and the gauge is unaffected.

## Session hints

In a local Kiro window on macOS (observed), Windows and Linux (enabled, not yet verified natively; the feature stays silent if the session files are laid out differently), Cyclegauge can show two short notices about your **most recent Kiro session in this workspace**. The feature is **on by default**; turn it off with the user setting `cyclegauge.sessionHints` or the **Turn off** button on a notice. It is a new read of Kiro's local session files, described exactly in [privacy and storage](privacy-and-storage.md) (it keeps only the model identifier, the context percentage and a time, and never stores or sends anything).

- **Context reminder:** at about 70 % "Kiro may compact it soon; consider starting a new session for unrelated work", and at about 85 % "close to its limit", each with "as of HH:MM" (your local time). The percentage is the latest value Kiro wrote for that session, a snapshot of the selected model's window, not Kiro's live meter, and it can fall after a model switch or compaction. The thresholds are educated guesses. A threshold fires once and is armed again after the value falls 10 points below it.
- **Model hint:** "set to Claude Sonnet 4.5 as of HH:MM. Kiro lists it at about 1.3x the credits of Auto (Kiro model table, as of 2026-10-18); actual credits per task vary." Only for models the in-extension table lists above 1.0x: the Claude Sonnet 4.5 and later Sonnet, the Opus models, Claude Fable 5.1, Kimi K3 and the GPT-5.6 Sol and Terra models (for GPT-5.6 the notice says "from about" because Kiro bills a higher factor above 272K tokens). Silent for Auto, anything unknown, models at or below 1.0x (such as Haiku, MiniMax, GLM, DeepSeek, Qwen, GPT-5.6 Luna) and the retired Claude Sonnet 4.0. Only Claude Sonnet 4.5 (and two cheaper MiniMax models) were seen in real session files; the identifiers of the other rows are taken from Kiro's documentation or derived from its published names, so a hint can be missing for them. After 90 days the table is treated as stale and the notice says to check Kiro's current table instead of giving a number.
- **Limits:** at most one notice per check; per session at most one in 30 minutes and three per run; only for sessions active after the window started and within about 10 minutes. The newest session of your open folder is found by its workspace path, so it is silent if the path forms differ, if the session is not among the 20 most recently changed, if its workspace folder holds more than 200 sessions, or after 12 hours without activity. Multi-root windows match any local folder. Remote, WSL, SSH, Windows and Linux windows are silent.
- If `~/.kiro` is a symlink, nothing is read. Kiro's files are Kiro's undocumented implementation detail and may change; the feature then goes silent. **Cyclegauge: Copy Diagnostics** shows only the last check's fixed code.

## Upgrading from 0.5.x

<a id="upgrading-from-052-or-an-earlier-build"></a>

Starting with 0.7.0 the extension stores its history in the editor's per-extension storage folder (`User/globalStorage/stefansuess.cyclegauge` under the editor's data root; on macOS `~/Library/Application Support/Kiro/User/globalStorage/stefansuess.cyclegauge`). An upgrade with blank storage settings therefore starts with no prior history or historical forecast coverage. Existing directories are not moved, imported or deleted.

Earlier locations: Cyclegauge 0.5.2 used the `EasyKiroGauge` directory; 0.5.3 used the `Cyclegauge` directory (on macOS `~/Library/Application Support/EasyKiroGauge` and `~/Library/Application Support/Cyclegauge`).

To keep using that history, disable any earlier extension first, then set **user-level** `cyclegauge.storageRoot` to the directory you previously used before activating this build, using the full canonical path. A chosen location must be outside Kiro's data folder; use only an existing Cyclegauge-owned directory, never Kiro-owned storage. The CLI can select it with `--store-dir`. Do not run two builds against the same directory at once; side-by-side installation is not blocked.

Transfer any explicit `easykirogauge.sourceRoot`, `easykirogauge.storageRoot` and `easykirogauge.sourceTimezone` values to the corresponding `cyclegauge.*` user settings. The old keys are no longer read; blank current settings use the default source, storage and device timezone. Replace custom `easykirogauge.showUsage` shortcuts with `cyclegauge.showUsage`, then reload the window.

## Upgrading from 0.7.x

By design, the storage location and store version are unchanged from 0.7.0, so existing history and forecast coverage should carry over without changing settings. A native upgrade test has not been recorded.

## Kiro Steering and Hooks review (unreleased)

Run **Cyclegauge: Review Kiro Steering and Hooks** (`cyclegauge.reviewKiroConfig`) from the Command Palette or the separate **Kiro Steering and Hooks** section in the **Kiro Workspace Audit** view. It also has its own button in the Audit view's title bar, and a **manual** workspace audit (the command, the Audit view button, the dashboard card's **Check now** link, **Run audit** in the reminder, or the credit view's **Show** when there is no audit result yet) runs it as well, with the same checks and limits, unless you dismiss the folder picker or cancel the audit (it still runs after an audit refusal or failure and then shows its own result or refusal); the filename audit's result and the review's result are shown separately, and a failure of one does not hide the other. It otherwise runs automatically only if you turn on `cyclegauge.configReviewAutomatically` (below). The audit's silent re-runs (automatic, reminder-driven, file-watcher or after an ignore-file change) never start a configuration review.

The review requires a trusted workspace. It checks at most eight local `file:` roots, deduplicated by real path, with the same per-root folder safety guards as the audit. Refused, nonlocal and excess roots appear under **Not checked**. It non-recursively lists `.kiro/steering/*.md` and `.kiro/hooks/*.json`; it reads the first few bytes of each Steering file, up to 2 KiB only when it starts with a front-matter block, parses Hook JSON files up to 64 KiB, and reads only root `AGENTS.md`'s size. It never reads global configuration in your home folder or nested `AGENTS.md`, resolves file references, or executes a hook. The shared per-run read budget is 3.6 MiB with a cooperative three-second time limit; unavailable or omitted data stays unknown.

The native plain-text tree shows escaped relative file names and root names. Hook names are capped at 60 code points before escaping and appear only in sidebar labels; tooltips and previews use ordinals. No Steering body, pattern, matcher, prompt or command text is kept or shown. Each finding distinguishes documented behavior from Cyclegauge heuristics or inference. Always-included size is a lower bound; the cross-root sum is labelled inference. There are no estimated credit savings.

Click a finding with a preview action to open a new unsaved plain-text document containing fixed guidance and relative file names only. Nothing in the workspace changes: review the guidance yourself before editing configuration. Disabling a hook loses its automation; Kiro CLI V1/V2 loads only always-included Steering automatically. The review has no clipboard action, persistence, dashboard summary or support-prompt effect. Results disappear on reload. Native Kiro, Windows and Ubuntu acceptance for this feature has not been recorded.

## Automatic Steering and Hooks review (opt-in, unreleased)

The user setting `cyclegauge.configReviewAutomatically` is **off** by default. Only your own user (global) value counts; a workspace's `.vscode/settings.json` cannot turn it on, and an unknown value counts as off. `onOpen` runs the same review once per window, about 45 seconds after a trusted workspace opens (staggered after the audit reminder). `onOpenAndChanges` also watches only root `AGENTS.md`, `.kiro/steering/*.md` and `.kiro/hooks/*.json` in each checked root, and re-runs after those files are created, changed or deleted. The watcher reads nothing itself; changes wait 5 seconds (at most 60 seconds during a stream of changes), automatic runs are at least 30 seconds apart, and after 20 automatic runs in a window the header says "automatic review paused (many changes)". Before every automatic run the setting, workspace trust and each root's folder guard are checked again; turning the setting off, losing trust or changing folders cancels a pending run and discards a running one. A manual run always wins and does not count toward the limit. Automatic runs use exactly the same allowlist and limits as the manual command.

Automatic runs are quiet: no progress message and no focus change. The first automatic run of a window only updates the view, and `onOpen` never shows a message. In `onOpenAndChanges`, a run after a file change shows one fixed message ("Cyclegauge found things to review in your Kiro Steering and Hooks.", with **Show**) only for a kind of finding not yet seen in this window: at most three per window, at least a minute apart, never for information-only findings or "not checked" results. Findings first seen after the window's first review are marked "new this session" in the view. All of this is in memory and resets when the window reloads. Editor watcher limits, `files.watcherExclude` or network drives can suppress change events; the header always shows how old the check is, and the manual command stays available. A file whose letter case differs from the pattern (for example `agents.md`) may not raise an event and is picked up by the next open or manual run.

After your first manual review, Cyclegauge may offer once ever to turn this on: "Check Kiro Steering and Hooks automatically in trusted workspaces you open, and when those files change?" **Turn on** writes `cyclegauge.configReviewAutomatically = onOpenAndChanges` to your user settings only; **Not now** changes nothing. The offer is not shown when `cyclegauge.supportPrompts` is off, when you already set the automatic setting yourself (including `off`), or while or within a minute of a support prompt.

## Workspace audit

Run **Cyclegauge: Audit Kiro Workspace** (command ID `cyclegauge.auditWorkspace`) from the command palette, or use **Check workspace** in the **Kiro Workspace Audit** view in the Explorer, or the **Check now** button of the Workspace check card in the credit view. It audits a trusted, local workspace folder (you choose one if several are open), and a progress notification lets you cancel. Results appear in the **Kiro Workspace Audit** view; its header (in the description) and the credit view's Workspace check card also show the total size, in B, KiB, MiB or GiB, of the files Kiro may read but probably does not need ("about", or "at least" when some sizes are unknown or the list is cut short); it is an exposure figure, not a saving or a measurement. **Cyclegauge: Show Workspace Audit** (or the card's **Show** button) opens that view, and runs the check first if there is no result yet.

What it does: it walks the folder reading only file names and sizes, plus the ignore files listed in Agent Ignore Files (`kiroAgent.agentIgnoreFiles`). It never reads other file contents, writes no files and sends nothing. Global ignore files are not read.

Reading the results:

- The first line is a summary: **N items Kiro may read** (optionally followed by **· M unclear**; if none are known to be unexcluded but some are unclear, **M items to review**) with the folder and when it was checked ("just now", "5 min ago", "today", "yesterday", "N days ago"; this time is kept only in memory for the current window), or **No risky files found** when nothing was listed. Hover it for what the count means and which reasons applied.
- Findings are grouped by kind (secrets and credentials, databases and dumps, archives, logs, large data files, build output, dependencies, other large files), each with a short reason such as "may contain passwords or keys". They are potential risks, not measured credit use, and being in the workspace does not mean Kiro read the file. Excluding files Kiro does not need keeps its context smaller and can save credits; no saving is measured.
- Each entry says **Kiro may read this** (no ignore file in this folder excludes it; global ignore files were not checked) or **Unclear** (Cyclegauge could not establish whether it is excluded, for example because a scan limit was reached or the setting could not be read; unclear is never treated as excluded or as safe). The size is in the tooltip. After you exclude an entry it reads "rule prepared (unsaved)" until you save the change.
- A partial check says "partial check" in the summary and lists the reasons in its tooltip, such as a file-count or time limit. Scan limits are 50,000 entries, depth 24 and 10 seconds.
- Detection is by file name and size only. A clean result does not prove there are no secrets.
- The contents of folders such as `.git`, `.ssh`, `.gnupg`, `.aws`, `node_modules`, `bower_components`, `jspm_packages`, `.terraform` and `.pnpm-store` are not scanned, and symbolic links are skipped. `.ssh`, `.gnupg` and `.aws` are listed as one secrets entry each, wherever they are; the dependency folders as one dependencies entry each, unless they are inside build output, which is then listed instead.
- Name patterns cover common key, keystore and password-manager files, credential stores (`.netrc`, `.pgpass`, `.git-credentials`, …), shell and database histories, Terraform state, VPN profiles and a few tool credential files, plus common build caches and dependency folders (`Pods`, `.yarn/cache`). Files that only *may* contain credentials, such as `settings.py` or `.npmrc`, are not listed, because Kiro usually needs them. The patterns are our own, informed by public name-based lists (shhgit, GitHub Linguist, github/gitignore).
- Only the first 200 findings are listed; the rest are counted.
- Some folders are refused: a filesystem root, your home folder or one containing it, folders overlapping Kiro data or Cyclegauge storage, folders inside `.kiro`, or inside `.git`, `.ssh`, `.gnupg`, `.aws`, dependency folders such as `node_modules` or `.terraform`, or `kiro-cli` folders, symbolic links, and untrusted workspaces. Only local folders are offered.

Acting on findings (buttons on each entry, and at the top of the view):

- **Exclude from Kiro** prepares a root-anchored `.kiroignore` line as an **unsaved** change: it opens `.kiroignore` with the line added, or an unsaved new `.kiroignore` if there is none. Review it and save it yourself; Cyclegauge does not save it. If your editor saves files automatically (`files.autoSave`), the lines open in a separate new tab instead, for you to copy into `.kiroignore`. **Exclude all from Kiro** does the same for every listed item.
- **Not a problem — hide** hides an item for this workspace. Only salted hashes are stored in the editor's per-workspace storage, never paths. The entry **N hidden by you** (**Show again**) brings them back. This does not exclude the file from Kiro.
- **Show in Explorer** reveals the file or folder in the Explorer without opening it.
- **Copy .kiroignore lines** copies the lines to the clipboard instead.

Suggestions include unclear findings, so review them before saving. "No safe rule could be suggested" appears when a path has unsafe characters or a rule would also match other files. According to Kiro's documentation (not verified by Cyclegauge), for Kiro IDE to use `.kiroignore` it must be listed in `kiroAgent.agentIgnoreFiles`; the view shows ".kiroignore isn't active yet" when a `.kiroignore` exists but is not listed, and opens that setting when you select it. Only this folder's ignore files are checked, not global ones. Excluding files can hide files Kiro needs, so add only what you want excluded.

Reminders and automatic runs: about 30 seconds after Kiro starts, Cyclegauge checks once whether the open workspace (a single trusted local folder) is due. A workspace that was never audited gets one prompt; afterwards you are reminded after `cyclegauge.auditReminderDays` days (default 30, 0 turns reminders off), with **Run audit**, **Later** (7 days) and **Don't remind me**. If you set `cyclegauge.auditAutomatically` to `onOpen` (default `off`; the earlier `true` also means `onOpen`), an audit that is at least one UTC day old runs silently with the same limits when the workspace opens, and only notifies you when it finds something; a never-audited workspace still asks first, and reminders off (0), a snooze or **Don't remind me** also stop automatic runs. `onOpenAndChanges` does the same and also watches that single folder for new files or folders matching the audit's own name patterns (not size-only "large files", and nothing inside folders the audit never enters). This happens only in a workspace that was audited before and is not snoozed or set to **Don't remind me**. A few seconds after such files stop appearing (at the latest about a minute into a steady stream), the folder is re-checked silently; if a new file is a secrets finding that was not in the previous result, you get at most one notice per window and UTC day. Name matching for the watcher may be case-sensitive on some systems, so an unusually capitalised file can wait for the next full check. The paths of new files stay in memory until that re-check; nothing new is stored. Both settings apply only from your user settings, so a repository cannot turn automatic runs on or reminders off. Per workspace only the last audit date, a snooze date and a do-not-remind flag are stored. **Cyclegauge: Reset workspace audit reminder** clears the snooze and the flag.

After a workspace has been checked in this window, saving `.kiroignore` (or a file named in Agent Ignore Files) in that folder, or changing `kiroAgent.agentIgnoreFiles`, re-runs the check of that same folder about a second later. The re-check shows no notification; like any completed check it updates the view and the Workspace check card and records the check date (which postpones the reminder). A prepared, unsaved **Exclude from Kiro** edit is kept. Other saves and settings start nothing, and a folder that has not been checked in this window is never re-checked.

The credit view (**Show Account Credits**) has a small **Workspace check** card below the main figures: it shows the number of items and when the check ran (or an invitation to check with the last check date in UTC, or "This folder can't be checked. Run Check now to see why."), with **Check now** and, once checked, **Show**. It shows no folder name or path and claims no measured savings. A **Cost Advisor** button at the top of the view opens the same Cost Advisor as the editor-title button and the status bar item. The view still runs no scripts; its only command links are these five Cyclegauge commands (`cyclegauge.costAdvisor`, `cyclegauge.auditWorkspace`, `cyclegauge.audit.show`, `cyclegauge.share`, `cyclegauge.reportProblem`), enabled through the webview's command allowlist, none with arguments. A quiet footer line also links to rating Cyclegauge on Open VSX, starring it on GitHub and supporting it on Ko-fi (fixed addresses, opened only when you click), plus **Share**, which copies a short fixed text with the Open VSX link to your clipboard, and **Report a problem**, which runs **Cyclegauge: Report a Problem** (see Diagnostics below).

The audit, Copy Diagnostics and the gauge of an earlier 0.9.0 candidate were tested by the maintainer in native Kiro on macOS; the audit view wording, the Workspace check card, the Exclude and hide actions, reminders, the footer links, Share, Report a Problem (including the error-notification button and opening the form), the support prompt, the re-check after ignore changes and the onOpenAndChanges watcher have not yet been verified in native Kiro, the "Kiro not detected" note and status have not been verified in any non-Kiro editor, and no 0.9.0 testing on Windows or Ubuntu is recorded. Earlier (0.7.0) testing is described in the changelog.

## Budget warnings

Inside Kiro, Cyclegauge can tell you early when your reported credits are running low, with a short message and two buttons: **Show details** (opens the credit view) and **Turn off** (sets `cyclegauge.budgetWarnings` to off in your user settings). There are three notices that warn about the limit and one that helps you save, all based only on a fresh account update (never on stale data):

- **Forecast**: a regular, current forecast (not a provisional early estimate) says the reported limit is reached before the reset: "At this pace your Kiro credits run out on {date}, {n} days before the reset."
- **Percent**: you have used the configured share of the reported limit (`cyclegauge.budgetWarningPercent`, default 80; 0 turns this notice off): "You have used {p}% of your reported Kiro credits ({used} of {limit}); the reset is in {n} days."
- **Limit**: usage has reached the reported limit: "You have reached the reported Kiro credit limit ({used} of {limit}); the reset is in {n} days."
- **Right-sizing** (lowest priority, only in the last 7 days before the reset): "You will likely leave about {n} credits unused this cycle, and the last cycle also fit within {Smaller plan}. {Smaller plan} would cost about ${x} a month less (modelled)." See below.

Each notice appears at most once per billing cycle (identified by the observed reset time) and at most one notice per window; if several are due at once, only the most severe (limit, then forecast, then percent, then right-sizing) is shown and the others count as handled. The status bar item turns red instead of yellow when the limit is reached or a regular forecast says it will be reached before the reset (a provisional estimate stays yellow); this colour is part of the gauge and is independent of `cyclegauge.budgetWarnings`. Accounts whose data includes extra credits, which Cyclegauge does not support, get no budget notices. Both settings are user-level only (a workspace cannot change them). The only state kept is the cycle and which notices were shown (see [privacy and storage](privacy-and-storage.md)); nothing is sent anywhere.

When the forecast or the observed usage goes beyond the reported limit, the credit view and the forecast and limit notices add a modelled cost, for example "If you continue at this pace: about 200 credits over the reported limit ≈ $8.00 at $0.04 per credit (price list 2026-10-10, reviewed 10 Oct 2026)"; the notices carry the same figure with the price and review date and the same qualifiers, and only after a regular forecast. It is projected credits over the limit times the per-credit price from Cyclegauge's reviewed price list, rounded to whole cents, and shown only when that price list is valid; otherwise only the credits are shown. It is a modelled scenario, not an invoice: whether overage applies depends on your plan and settings, and the reported limit is not verified as base-only or total capacity. Usage already above the limit at the last update gets its own line ("{n} credits above the reported limit at the last update ≈ $x ... (modelled; whether overage applies depends on your plan and settings)"), which is left out for accounts with extra credits.
Two plan facts accompany these figures. Both are modelled or list-price information, not advice, and nothing is shown whenever an input is unknown. If your plan is only inferred from the reported limit, the sentences name it ("For comparison, if you are on {Plan}: …" and "If you are on {Plan}: …").

- **Next larger plan** (beside a projected overage): the credit view adds, right after the projected-overage line, "For comparison: {Next plan} costs ${x} a month more than {Current plan} and includes {n} more credits (list prices, price list reviewed {date}).", and the forecast and limit notices that carry an overage cost append the short form "For comparison: {Next plan} costs ${x} a month more and includes {n} more credits." These are only the two differences from Cyclegauge's reviewed price list: no recommendation and no claim that switching would save money. Nothing is shown for Power (no larger plan), when your plan is unknown, for accounts with extra credits, or when the price list is invalid.
- **Plan right-sizing** (read-only on the Cost Advisor's 1-month comparison, so it appears only with a regular forecast and a usable comparison that shows a saving): when the forecast leaves part of your limit unused, a smaller plan would cost less, and the last completed billing cycle also ended within that plan's credits, the credit view shows the sentence above at any time; the notice appears only in the last 7 days before the reset, once per cycle. The size threshold is deliberate: the smaller plan must cover the projected usage, so the unused part is at least the gap between the two plans. "The last cycle fit" means the last cycle's observed usage plus an allowance for its last unobserved hours (the gap from the last observation to the reset at that cycle's average pace). Observed usage is taken from the stored history only where the cycle's start and every step are backed by observations, so this needs three observed billing cycles, and nothing is shown when anything is missing. Unused credits are rounded down. Moving to Free is never suggested. It is a modelled comparison, not advice to change plan: check your real plan, add-on credits and Kiro's terms first.

No plan is ever changed by Cyclegauge.

## Support prompts

Besides the footer in the credit view, Cyclegauge may ask once per window, inside Kiro only, “Finding Cyclegauge useful? Rate it or support development. Turn off reminders in Cyclegauge settings.” The buttons are **Rate**, **Support** and **Later**. Rate opens the Open VSX review page; Support opens Ko-fi. Either action snoozes the prompt for 120 days; **Later** or closing the message snoozes it for 60 days. It can appear about one minute after you save an **Exclude from Kiro** edit, once at least one UTC day has passed since first use. Opening **Show Account Credits** on three distinct UTC days or completing a Cost Advisor review can also trigger it earlier, without a seven-day wait. Opening or cancelling the Advisor, or clearing its answers, does not count. Otherwise, the fallback check is about three minutes after start, at least seven UTC days after first use and only after a forecast or audit finding was shown. A pending saved-exclusion prompt waits its full minute unless a separate medium signal qualifies. Turn it off at any time with the user setting `cyclegauge.supportPrompts` (a workspace cannot change it). Existing users who selected **Don't ask again** remain opted out; **Cyclegauge: Reset Support Prompts** (command `cyclegauge.support.reset`, in the Command Palette) clears all saved support dates and flags, including that legacy opt-out, detail-view days and Advisor-used flag. Reset does not allow a second prompt in the same window. Prompt state is only dates (at most three detail-view days) and flags in the editor's global storage. Nothing is sent anywhere; a link opens only when you click it.

Maintainer native test (synthetic profile only): run `CYCLEGAUGE_SYNTHETIC_SUPPORT_TEST=1 pnpm demo:setup --open --vsix <candidate.vsix>` on macOS/Linux (PowerShell: `$env:CYCLEGAUGE_SYNTHETIC_SUPPORT_TEST='1'; pnpm demo:setup --open --vsix <candidate.vsix>`). The generated opener supplies a marker matching the demo source; the extension also requires the isolated demo home and global storage. Install the supplied candidate in that demo window, run **Reset Support Prompts**, create an invented `.env` in the demo workspace, run the audit, choose **Exclude from Kiro**, then save as `.kiroignore` in that workspace. The prompt should appear about a minute later. This opt-in only treats first use as yesterday; it preserves the setting, Kiro detection, snoozes, never flag and once-per-window limit. A reload is needed to test another prompt after one has appeared. Without the explicit flag, the demo uses ordinary timing. No native verification of this change is claimed.

In an editor that is not Kiro (and without `cyclegauge.sourceRoot`), when Cyclegauge finds no Kiro logs it shows "Kiro not detected" in the status bar, says the same in the credit view and explains once that it is built for Kiro. If Kiro is installed next to that editor and its logs are found, it works normally and shows no note. The workspace audit still works.

## Diagnostics

Run **Cyclegauge: Copy Diagnostics** (`cyclegauge.copyDiagnostics`) to open the report in an unsaved document and copy it to the clipboard. The extension command writes no file. To report a problem, run **Cyclegauge: Report a Problem** (`cyclegauge.reportProblem`), or choose the **Report a problem** button on one of Cyclegauge's own error notifications or the **Report a problem** link at the bottom of the credit view. It builds the same report, opens it in an unsaved document for review, copies it to the clipboard and then opens Cyclegauge's fixed GitHub bug-report form in your browser, where you can paste the report. Nothing is put in the address and nothing is sent by Cyclegauge. Alternatively run the CLI with `--diagnostics`: it first performs the normal import into Cyclegauge's own store and writes nothing else.

The report contains only fixed codes, counts and platform metadata: Cyclegauge, editor and editor version, Node and Electron versions, platform, architecture, SQLite availability, store state and version, whether storage, source and timezone are default or chosen, status and forecast tier, gauge state, whether the audit is available, counts of snapshots, accounts and unassociated snapshots, a collection result (CLI only), a freshness bracket, import codes and a discovered-log count. It contains no paths, identifiers, amounts or log content. Review it before pasting it into an issue.

## Requirements and command-line tool

Node.js **24.13 or newer**. Runtime uses built-in modules only; TypeScript and Node type definitions are development dependencies. Install development tools with `pnpm install --frozen-lockfile`.

Run from this checkout:

```sh
node --disable-warning=ExperimentalWarning src/cli.ts --source-timezone Europe/Berlin
node --disable-warning=ExperimentalWarning src/cli.ts --source-timezone Europe/Berlin --json
node --disable-warning=ExperimentalWarning src/cli.ts --help
```

Declare the timezone actually used by the source logs. Europe/Berlin is supported by the discovery observation, not a universal default. Offset-free timestamps without a declared IANA timezone are unavailable. DST overlaps and nonexistent wall times are rejected rather than guessed. Offset-aware timestamps preserve their spelling and normalize their instant to UTC.

Options:

| Option | Purpose |
| --- | --- |
| `--source-root <directory>` | Override the Kiro IDE data root, containing `logs/` |
| `--source-timezone <IANA>` | Interpret offset-free source timestamps |
| `--store-dir <directory>` | Dedicated private app-owned directory outside the source `logs/` and Git repositories |
| `--max-age-hours <hours>` | Observation freshness threshold, default 24; operational policy, not measured service latency |
| `--diagnostics` | Print the diagnostics report (fixed codes and counts); first performs the normal import into Cyclegauge's own store |
| `--json` | Local billing/quality query output without account, source or deduplication keys |

Default source candidates: macOS `~/Library/Application Support/Kiro`; Windows `%APPDATA%\Kiro`; Linux `${XDG_CONFIG_HOME:-~/.config}/Kiro`. Only `logs/<run>/<window>/exthost/kiro.kiroAgent/q-client.log` and numeric suffixes such as `q-client.log.1` are read. These suffixes are an explicitly supported synthetic rotation convention, not a verified Kiro rotation contract.

Default owned storage. **Extension:** the editor's own per-extension storage folder, `User/globalStorage/stefansuess.cyclegauge` beneath the editor's data root, like other extensions (on macOS `~/Library/Application Support/Kiro/User/globalStorage/stefansuess.cyclegauge`). **CLI** (no editor available): macOS `~/Library/Application Support/Cyclegauge`; Linux `${XDG_DATA_HOME:-~/.local/share}/Cyclegauge`; Windows `%LOCALAPPDATA%\Cyclegauge`. The two defaults differ, so pass `--store-dir` to query the extension's store from the CLI. On POSIX, storage must have owner-only access. A chosen location must be outside the source root. On Windows the defaults rely on the user profile's permissions only when the editor's data folder is inside the user profile (a portable install or a custom `--user-data-dir` on a shared drive is not protected), and a chosen location is verified (see [platform verification](platform-verification.md)). The source `logs/` folder, anything containing the source root, Git repositories, symlink paths and `kiro-cli`/`.kiro` directories are rejected as store locations. On macOS, use canonical paths when a path includes system aliases such as `/tmp` or `/var`.

The CLI prints observed usage, reported limit, remaining reported credits, reset UTC instant, as-of time, quality flags and fixed import diagnostic codes. A successful query exits 0 even when values are unavailable; configuration, storage or fatal collection failures exit 1 with a fixed code. JSON output follows the same policy.

## Troubleshooting

- **"Collecting data" for a long time.** The extension only reads usage that Kiro has already written to its logs. Wait for the next scan, which runs every minute and when log files change. A forecast additionally needs several observations over days; see [forecasting.md](forecasting.md).
- **"Unavailable".** The logs could not be read or have an unsupported format, the storage location is not safe (for example on Windows a chosen storage location that cannot be verified is refused, or a path containing a symlink), or several accounts were detected. No numbers are invented in these cases.
- **Settings changes do not apply.** `cyclegauge.sourceRoot`, `cyclegauge.storageRoot` and `cyclegauge.sourceTimezone` are read when the extension activates. Reload the window after changing them.
- **"Kiro: update needed".** The runtime has no SQLite support, or the stored data was written by a newer Cyclegauge. Update Kiro or Cyclegauge; stored data is never modified. **Cyclegauge: Copy Diagnostics** shows which case applies.
- **Node.js.** Node.js 24.13+ is required to build and for the CLI. The installed extension runs inside Kiro's own extension host; which Node features that host provides has only been observed on Kiro 1.2.56 (macOS), and no minimum Kiro version is established.
- **Remote or SSH workspaces.** Not verified. The extension is declared as a UI extension that reads local files.
- **Removing local data.** Delete the storage folder listed under "Default owned storage" above. Kiro's own files are never touched.
