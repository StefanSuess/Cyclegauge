# Installing and using Bobert: Kiro Credit Tracker

> Extension ID: `StefanSuess.bobert`; commands and settings use the `bobert.*` prefix.

## Install from Open VSX or build a development VSIX

Bobert is available on [Open VSX](https://open-vsx.org/extension/StefanSuess/bobert) and under [GitHub Releases](https://github.com/StefanSuess/Bobert/releases). To test unreleased changes, build a VSIX from a checkout (Node.js 24.13 or newer and pnpm):

```sh
pnpm install --frozen-lockfile
pnpm package:vsix
```

Then run **Extensions: Install from VSIX...** in Kiro and select the file in `dist/`. Reload the window if Kiro asks, then open **Bobert: Show Credit Budget** (command ID `bobert.showUsage`) or click the status-bar item. This command only opens the local billing view.

Settings: `bobert.sourceRoot`, `bobert.storageRoot`, and `bobert.sourceTimezone`. Blank settings use the platform's default IDE/app-owned locations and device timezone. `bobert.sourceRoot` exists for testing and demos with synthetic logs; normal use leaves it blank. Offset-free historical log timestamps may be ambiguous if the device timezone changed. Stale or unavailable values are labeled. CLI and Crew session metering and add-on balance aggregation are not read.

The Settings editor lists the settings you are most likely to change first (budget notices, session hints, audit reminders, automatic runs, support prompts); the three testing and storage overrides come last.

| Setting | Scope | Default | Purpose |
| --- | --- | --- | --- |
| `bobert.sourceRoot` | machine | empty | Synthetic logs for tests and demos; empty reads Kiro's standard data folder |
| `bobert.storageRoot` | machine | empty | Private Bobert storage folder; empty uses the editor's per-extension storage |
| `bobert.sourceTimezone` | machine | empty | IANA timezone for offset-free log timestamps; empty uses the device timezone |
| `bobert.auditReminderDays` | user | 30 | Days between workspace audit reminders; 0 turns them off |
| `bobert.auditAutomatically` | user | `off` | Shown as Off / On open / On open and on changes (values `off`, `onOpen`, `onOpenAndChanges`). `onOpen`: silently re-run an audit older than one day when the workspace opens; `onOpenAndChanges`: also re-check when matching files appear |
| `bobert.supportPrompts` | user | on | The occasional rate-or-support reminder, the one-time offer of the automatic Steering and Hooks review, the first-use walkthrough and the Open VSX link line on the shareable recap; off stops all of these (not budget notices, session hints or audit reminders) |
| `bobert.budgetWarnings` | user | on | Budget notices inside Kiro, including the right-sizing tip (see Budget warnings); off stops them |
| `bobert.sessionHints` | user | on | Session hints (macOS observed, Windows and Linux enabled, not yet verified natively): context reminder and model hint from your newest Kiro session (see Session hints); off stops all reading |
| `bobert.budgetWarningPercent` | user | 80 | Share of the reported credit limit (0 to 100) at which the early notice appears; 0 turns only that notice off |

## Getting started

After installation, new users inside Kiro get a short walkthrough, **Get started with Bobert**, opened once. It shows where your Kiro credits are (and that a forecast appears after a few days of usage: a provisional estimate after about 2 days and 3 updates, a regular forecast after 7 days and 8 updates), offers the workspace audit right away (it needs no usage history), points to the Cost Advisor and the Steering and Hooks review, to the budget warning settings, and explains the session hints (short here; the exact reads are in [privacy and storage](privacy-and-storage.md)). The credits, audit and savings steps are marked done when you run their command; the budget and session-hint steps when you select them. The first-time audit reminder does not also appear in the window where the walkthrough opened; it waits for the next window. Open it any time with **Bobert: Get Started** (command ID `bobert.gettingStarted`). Users who already had Bobert (any earlier Bobert state) and users who turned `bobert.supportPrompts` off are not shown it, and it never opens outside Kiro or in extension tests. Only one flag is stored (see [privacy and storage](privacy-and-storage.md)). Walkthrough support is not yet verified in native Kiro; if the editor cannot open it, nothing happens and the gauge is unaffected.

## Credit dashboard

**Bobert: Show Account Credits** (or a click on the status-bar item) opens the credit dashboard. It runs one bundled script under a strict content security policy that blocks all network connections; see [privacy and storage](privacy-and-storage.md). It is built only from what Kiro has logged and Bobert has stored, and gaps are shown as unknown, never as zero.

- **Usage chart.** Hover or keyboard focus shows a tooltip for each point (arrow keys move between points, Escape closes it), with forecast scenarios when there is enough history. A data table accompanies the chart.
- **Today's pace.** The observed net change within the UTC day, with its start and elapsed time. It is never extrapolated.
- **Cycle comparison.** Compares with the previous billing cycle at the same elapsed point, only where both cycles have evidence-backed starts; otherwise it shows the bracketing observations or "not comparable".
- **Cost Advisor.** An inline form with the same result as the native pickers. Answers stay session-only and are never persisted.
- **Your Bobert summary.** The exclusions you saved in the observed cycle (items, possible secrets, known bytes, as a lower bound when sizes are unknown) and an observed-use trend against the preceding period. Gaps read "not observed" or "not comparable"; no "saved credits" are estimated.
- **Your Kiro cycle (recap).** When a new billing cycle is first observed and the previous one has an evidence-backed start and end, a dismissible card shows credits used, whether they lasted until the reset (yes, no or unknown), the comparable trend, the exclusions you saved and the busiest observed UTC day (a partial observation). Preview it, then **Save image…** (a save dialog; guarded target) or **Copy text**. It contains no identifiers, paths or workspace names.
- **Export CSV…** writes your own accepted history to a file you choose: allowlisted columns, exact decimals, `unknown` instead of zero, no free text. With several or unknown accounts a fixed message replaces the export.
- **Live updates.** The view refreshes as new observations arrive.

Native verification of the dashboard on Windows and Ubuntu is not recorded.

## Session hints

In a local Kiro window on macOS (observed), Windows and Linux (enabled, not yet verified natively; the feature stays silent if the session files are laid out differently), Bobert can show two short notices about your **most recent Kiro session in this workspace**. The feature is **on by default**; turn it off with the user setting `bobert.sessionHints` or the **Turn off session hints** button on a notice. It is a new read of Kiro's local session files, described exactly in [privacy and storage](privacy-and-storage.md) (it keeps only the model identifier, the context percentage and a time, and never stores or sends anything).

- **Context reminder:** at about 70 % "Kiro may compact it soon; consider starting a new session for unrelated work", and at about 85 % "close to its limit", each with "as of HH:MM" (your local time). The percentage is the latest value Kiro wrote for that session, a snapshot of the selected model's window, not Kiro's live meter, and it can fall after a model switch or compaction. The thresholds are educated guesses. A threshold fires once and is armed again after the value falls 10 points below it.
- **Model hint:** only when there is a reason for it (maintainer decision 2026-10-20): your credit budget is tight (the status bar shows a warning or the reported limit is reached; never from stale or unavailable data) **or** the session is at least 30 % full. For example "Your Kiro credit budget is tight, and your most recent session in this workspace uses Claude Sonnet 4.5 (as of HH:MM), which Kiro lists at about 1.3x the credits of Auto (Kiro model table, as of 2026-10-18). For routine steps, Auto or a lighter model uses fewer credits; actual credits per task vary." or, for a long session, "…is getting long and uses Claude Sonnet 4.5…". Its buttons are **Show credit budget**, **Tips** (opens [Spend fewer Kiro credits](credit-tips.md) on GitHub, a fixed address opened only when you click) and **Turn off session hints**. Once per model per window; nothing is stored. Only for models the in-extension table lists above 1.0x: the Claude Sonnet 4.5 and later Sonnet, the Opus models, Claude Fable 5.1, Kimi K3 and the GPT-5.6 Sol and Terra models (for GPT-5.6 the notice says "from about" because Kiro bills a higher factor above 272K tokens). Silent for Auto, anything unknown, models at or below 1.0x (such as Haiku, MiniMax, GLM, DeepSeek, Qwen, GPT-5.6 Luna) and the retired Claude Sonnet 4.0. Only Claude Sonnet 4.5 (and two cheaper MiniMax models) were seen in real session files; the identifiers of the other rows are taken from Kiro's documentation or derived from its published names, so a hint can be missing for them. After 90 days the table is treated as stale and the notice says to check Kiro's current table instead of giving a number.
- **Limits:** at most one notice per check; per session at most one in 30 minutes and three per run; only for sessions active after the window started and within about 10 minutes. The newest session of your open folder is found by its workspace path, so it is silent if the path forms differ, if the session is not among the 20 most recently changed, if its workspace folder holds more than 200 sessions, or after 12 hours without activity. Multi-root windows match any local folder. Remote, WSL, SSH, Windows and Linux windows are silent.
- If `~/.kiro` is a symlink, nothing is read. Kiro's files are Kiro's undocumented implementation detail and may change; the feature then goes silent. **Bobert: Copy Diagnostics** shows only the last check's fixed code.

## Settings and defaults

The settings are `bobert.sourceRoot`, `bobert.storageRoot` and `bobert.sourceTimezone`, plus the user-level settings below (a workspace cannot change them):

- **On by default:** `bobert.budgetWarnings` (on), `bobert.budgetWarningPercent` (80), `bobert.supportPrompts` (on), `bobert.auditReminderDays` (30, 0 = off) and `bobert.sessionHints` (on; macOS observed, Windows and Linux enabled but not natively verified).
- **Off by default:** `bobert.auditAutomatically` (`off`) and `bobert.configReviewAutomatically` (`off`).

You may see budget notices, an occasional support prompt and (once, for a workspace that was never checked) an audit reminder; on macOS session hints read Kiro's session metadata (see Session hints and [privacy and storage](privacy-and-storage.md)). The walkthrough opens once. The new saved state is small (dates and flags in the editor's own storage); **Bobert: Reset Support Prompts and Summary** clears the prompt, summary and recap state.

## Compatibility in 1.x

From 1.0.0 these are kept stable: they are not removed or renamed within 1.x, and a breaking change needs a new major version. New commands, settings and output fields may be added. This section lists what the code and manifest contain today.

- **Command IDs** (all contributed by the extension manifest). Command IDs only; command arguments (for example audit tree items) are not part of the promise: `bobert.showUsage`, `bobert.costAdvisor`, `bobert.auditWorkspace`, `bobert.reviewKiroConfig`, `bobert.copyDiagnostics`, `bobert.reportProblem`, `bobert.audit.accept`, `bobert.audit.dismiss`, `bobert.audit.reveal`, `bobert.audit.acceptAll`, `bobert.audit.copy`, `bobert.audit.clearDismissed`, `bobert.audit.show`, `bobert.audit.resetReminder`, `bobert.share`, `bobert.support.reset` and `bobert.gettingStarted`. Internal handlers that are not in the manifest (for example the Steering and Hooks preview action) are not part of the promise.
- **Setting keys** and their scopes: `bobert.sourceRoot`, `bobert.storageRoot` and `bobert.sourceTimezone` (machine); `bobert.auditReminderDays`, `bobert.auditAutomatically` (`off`, `onOpen`, `onOpenAndChanges`; the earlier `true` means `onOpen`), `bobert.supportPrompts`, `bobert.configReviewAutomatically` (`off`, `onOpen`, `onOpenAndChanges`), `bobert.budgetWarnings`, `bobert.sessionHints` and `bobert.budgetWarningPercent` (user level). Existing values keep their meaning.
- **CLI options and JSON output.** The options `--source-root`, `--source-timezone`, `--store-dir`, `--max-age-hours`, `--diagnostics`, `--json` and `--help` keep their meaning. With `--json` the top-level fields are `observation`, `import`, `cache`, `platform` and `platformVerification`; inside `observation` the fields are `history`, `forecast`, `status`, `source`, `observedAt`, `observedText`, `sourceTimezone`, `usage`, `baseLimit`, `remainingBaseCredits`, `resetAt`, `resetText`, `availablePerDay`, `allocationBasis`, `totalAvailableCredits`, `dailyConsumption`, `flags` and `interval` (`status`, `netChange`, `dailyConsumption`). Fields are not removed or renamed; the nested `history` and `forecast` objects may gain fields. Exit code 1 with a fixed code still signals configuration, storage or collection failure.
- **Storage location.** The extension keeps using the editor's per-extension storage folder (`User/globalStorage/stefansuess.bobert`) unless `bobert.storageRoot` is set; the CLI keeps its application-data directory (see Default owned storage below).
- **Store versioning.** The store carries a version (currently 1). An older store is upgraded by an ordered, transactional migration list; a store written by a newer Bobert is refused with the fixed code `STORAGE_NEWER` (status bar "Kiro: update needed"), is never modified, and you can use it again after updating Bobert. Kiro's own files are never changed.

Not promised: the wording of messages and views, the audit's name patterns, the model table of the session hints, the price list and the forecast thresholds (they follow Kiro and are reviewed over time), and anything that depends on Kiro's undocumented log and session formats.

## Kiro Steering and Hooks review

Run **Bobert: Review Kiro Steering and Hooks** (`bobert.reviewKiroConfig`) from the Command Palette. Its results appear in the **Workspace Audit** view, in the groups described below; there is no separate button for it in the view, because the view's one refresh button runs both. A **manual** workspace audit (the command, the Workspace Audit view button, the dashboard card's **Run audit** link, **Run audit** in the reminder, or the credit view's **Show** when there is no audit result yet) runs it as well, with the same checks and limits, unless you dismiss the folder picker or cancel the audit (it still runs after an audit refusal or failure and then shows its own result or refusal); the filename audit's result and the review's result are shown in the same view, and a failure of one does not hide the other. It otherwise runs automatically only if you turn on `bobert.configReviewAutomatically` (below). The audit's silent re-runs (automatic, reminder-driven, file-watcher or after an ignore-file change) never start a configuration review.

The review requires a trusted workspace. It checks at most eight local `file:` roots, deduplicated by real path, with the same per-root folder safety guards as the audit. Refused, nonlocal and excess roots appear under **Not checked**. It non-recursively lists `.kiro/steering/*.md` and `.kiro/hooks/*.json`; it reads the first few bytes of each Steering file, up to 2 KiB only when it starts with a front-matter block, parses Hook JSON files up to 64 KiB, and reads only root `AGENTS.md`'s size. It never reads global configuration in your home folder or nested `AGENTS.md`, resolves file references, or executes a hook. The shared per-run read budget is 3.6 MiB with a cooperative three-second time limit; unavailable or omitted data stays unknown.

The native plain-text tree shows escaped relative file names and root names. Technical terms such as `inclusion: manual` or `trigger: Manual` appear only in tooltips and in the change preview, never in headings. Hook names are capped at 60 code points before escaping and appear only in sidebar labels; tooltips and previews use ordinals. No Steering body, pattern, matcher, prompt or command text is kept or shown. Each finding distinguishes documented behavior from Bobert heuristics or inference. Always-included size is a lower bound; the cross-root sum is labelled inference. There are no estimated credit savings.

The review's findings are grouped by what Bobert suggests doing, each group with a button that names its verb (see [Workspace audit](#workspace-audit)). Items are sorted by impact, largest first:

- **Load only when needed** (large always-included Steering file: no front matter, or `inclusion: always`): **Load only when needed…** inserts the front matter `---`, `inclusion: manual`, `---` at the start of the file, or changes the existing `inclusion` value. Kiro then includes the file only when you reference it with `#`. Alternatives (in the tooltip): `fileMatch` for specific files, or split the file.
- **Run only manually** (hooks that start an agent, on file changes, tool use or prompts): **Run only manually…** changes that hook's `trigger` to `"Manual"`, so it runs only when you start it. Only that hook's entry changes, never the rest of the file. Alternatives: narrow the matcher, use a shell command action, or **Disable hook** (in the item's right-click menu), which sets `"enabled": false` (or adds it). Disabling or running manually loses the automation.
- **Worth a look** makes no automatic change: a large `AGENTS.md` (**Show file** only, because Kiro has no inclusion modes for it), a Steering file whose `fileMatch` pattern matches every file (**Narrow the pattern** opens the file and selects the pattern value for you to type over; no pattern is suggested), and the combined-size and overlapping-hook findings, which span several files and keep **Show suggestion**, an unsaved plain-text note with fixed guidance and relative file names only.

These buttons work only in a trusted workspace and only if the file is still exactly what the review read (size, modification time and the bytes the review read); otherwise a fixed message asks you to run the review again. For a whole group, an item whose file changed, has unsaved changes or is saved automatically is skipped and counted ("K items skipped because they changed or are unsaved"); the rest are prepared. If the exact place cannot be found safely (for example duplicate keys or unusual formatting in a hook file), the file is opened without a change and a fixed message says so. If your editor saves files automatically, or the file has unsaved changes, nothing is prepared for that file and (for a single item) the file is only opened. Files not encoded as UTF-8 may be re-encoded by the editor when you save the prepared edit, so check the change before saving. The editor loads the opened file as it does when you open it yourself; Bobert's code reads no file text beyond the approved Steering prefix and Hook JSON. Kiro CLI V1/V2 loads only always-included Steering automatically. The review has no clipboard action, persistence, dashboard summary or support-prompt effect. Results disappear on reload. Native Kiro, Windows and Ubuntu acceptance for this feature has not been recorded.

## Automatic Steering and Hooks review (opt-in)

The user setting `bobert.configReviewAutomatically` is **off** by default. Only your own user (global) value counts; a workspace's `.vscode/settings.json` cannot turn it on, and an unknown value counts as off. `onOpen` runs the same review once per window, about 45 seconds after a trusted workspace opens (staggered after the audit reminder). `onOpenAndChanges` also watches only root `AGENTS.md`, `.kiro/steering/*.md` and `.kiro/hooks/*.json` in each checked root, and re-runs after those files are created, changed or deleted. The watcher reads nothing itself; changes wait 5 seconds (at most 60 seconds during a stream of changes), automatic runs are at least 30 seconds apart, and after 20 automatic runs in a window the header says "automatic review paused (many changes)". Before every automatic run the setting, workspace trust and each root's folder guard are checked again; turning the setting off, losing trust or changing folders cancels a pending run and discards a running one. A manual run always wins and does not count toward the limit. Automatic runs use exactly the same allowlist and limits as the manual command.

Automatic runs are quiet: no progress message and no focus change. The first automatic run of a window only updates the view, and `onOpen` never shows a message. In `onOpenAndChanges`, a run after a file change shows one fixed message ("Bobert found things to review in your Kiro Steering and Hooks.", with **Show**) only for a kind of finding not yet seen in this window: at most three per window, at least a minute apart, never for information-only findings or "not checked" results. Findings first seen after the window's first review are marked "new this session" in the view. All of this is in memory and resets when the window reloads. Editor watcher limits, `files.watcherExclude` or network drives can suppress change events; the header always shows how old the check is, and the manual command stays available. A file whose letter case differs from the pattern (for example `agents.md`) may not raise an event and is picked up by the next open or manual run.

After your first manual review, Bobert may offer once ever to turn this on: "Check Kiro Steering and Hooks automatically in trusted workspaces you open, and when those files change?" **Turn on** writes `bobert.configReviewAutomatically = onOpenAndChanges` to your user settings only; **Not now** changes nothing. The offer is not shown when `bobert.supportPrompts` is off, when you already set the automatic setting yourself (including `off`), or while or within a minute of a support prompt.

## Workspace audit

Run **Bobert: Run Workspace Audit** (command ID `bobert.auditWorkspace`) from the command palette, or use **Run the workspace audit** in the **Workspace Audit** view in the Explorer (the view offers it only with a trusted folder open; without a folder it offers **Open Folder**, and in an untrusted workspace **Manage Workspace Trust**), or **Run audit** on the Workspace audit card in the credit view. It audits a trusted, local workspace folder (you choose one if several are open), and a progress notification lets you cancel. Results appear in the **Workspace Audit** view (the one refresh button in its title bar, **Run Workspace Audit**, runs the audit and the Steering and Hooks review); its status line and the credit view's Workspace audit card also show the total size, in B, KiB, MiB or GiB, of the files Kiro may read but probably does not need ("about", or "at least" when some sizes are unknown or the list is cut short); it is an exposure figure, not a saving or a measurement. **Bobert: Show Workspace Audit Results** (or the card's **Show results** button) opens that view, and runs the check first if there is no result yet.

What it does: it walks the folder reading only file names and sizes, plus the ignore files listed in Agent Ignore Files (`kiroAgent.agentIgnoreFiles`). It never reads other file contents, writes no files and sends nothing. Global ignore files are not read.

Reading the results:

- The first line is the status: **Checked 19:42 · 9 suggestions** (the local time of the check when it was today, otherwise "yesterday" or "N days ago"; this time is kept only in memory for the current window), or **· nothing to suggest** when nothing was listed. Its description adds **Kiro may read about 12.0 MiB** ("at least" when some sizes are unknown or the list is cut short), when the checks run again by themselves (for example **checks again on open and on changes**, from `bobert.auditAutomatically` and `bobert.configReviewAutomatically`) and **partial check**. Hover it for the folder, what the count means and which reasons applied. After **Review changes…** it also says **· 1 file with unsaved prepared changes** (N files) until those files are saved, closed or reverted. Suggestions are the filename findings plus the Steering and Hooks findings.
- The suggestions are grouped by what Bobert suggests doing; the heading is the verb: **Exclude from Kiro** (adds lines to `.kiroignore`), **Load only when needed**, **Run only manually** and **Worth a look** (no automatic change), then **Not checked**. Every group and sub-group starts **collapsed**, and the editor keeps what you open across refreshes; the status line and warnings stay visible. A group that can change something has no extra note row: its tooltip gives the short why, the alternatives and "Nothing changes until you save." When Agent Ignore Files (`kiroAgent.agentIgnoreFiles`) is empty or does not list `.kiroignore`, the **Exclude from Kiro** group says "won't take effect yet — add .kiroignore to Agent Ignore Files" with a warning icon and starts with the row **Add .kiroignore to Agent Ignore Files…**, which only opens that setting (Bobert never changes settings); there is no separate top-level note for those two states while the group is listed.
- Inside **Exclude from Kiro**, findings are grouped by kind (secrets and credentials, databases and dumps, archives, logs, large data files, build output, dependencies, other large files), each with a short reason such as "may contain passwords or keys"; the largest items come first. They are potential risks, not measured credit use, and being in the workspace does not mean Kiro read the file. Excluding files Kiro does not need keeps its context smaller and can save credits; no saving is measured.
- Each entry says **Kiro may read this** (no ignore file in this folder excludes it; global ignore files were not checked) or **Unclear** (Bobert could not establish whether it is excluded, for example because a scan limit was reached or the setting could not be read; unclear is never treated as excluded or as safe). The size is in the tooltip. After **Review changes…** an item whose file now holds your unsaved change reads "prepared — save the file to apply" (with a different icon), for Exclude, Load only when needed and Run only manually alike. The mark is kept only in memory and disappears when you save, close or revert the file (a revert is noticed about half a second after the file becomes clean). A new `.kiroignore` that does not exist yet (an unsaved untitled document) is not tracked this way, so its items keep "rule prepared (unsaved)" until the next check.
- A partial check says "partial check" in the summary and lists the reasons in its tooltip, such as a file-count or time limit. Scan limits are 50,000 entries, depth 24 and 10 seconds.
- Detection is by file name and size only. A clean result does not prove there are no secrets.
- The contents of folders such as `.git`, `.ssh`, `.gnupg`, `.aws`, `node_modules`, `bower_components`, `jspm_packages`, `.terraform` and `.pnpm-store` are not scanned, and symbolic links are skipped. `.ssh`, `.gnupg` and `.aws` are listed as one secrets entry each, wherever they are; the dependency folders as one dependencies entry each, unless they are inside build output, which is then listed instead.
- Name patterns cover common key, keystore and password-manager files, credential stores (`.netrc`, `.pgpass`, `.git-credentials`, …), shell and database histories, Terraform state, VPN profiles and a few tool credential files, plus common build caches and dependency folders (`Pods`, `.yarn/cache`). Files that only *may* contain credentials, such as `settings.py` or `.npmrc`, are not listed, because Kiro usually needs them. The patterns are our own, informed by public name-based lists (shhgit, GitHub Linguist, github/gitignore).
- Only the first 200 findings are listed; the rest are counted.
- Some folders are refused: a filesystem root, your home folder or one containing it, folders overlapping Kiro data or Bobert storage, folders inside `.kiro`, or inside `.git`, `.ssh`, `.gnupg`, `.aws`, dependency folders such as `node_modules` or `.terraform`, or `kiro-cli` folders, symbolic links, and untrusted workspaces. Only local folders are offered.

Acting on findings. Each group heading is the verb, and the diff-icon button on the group and on each of its items does exactly that verb and says so in its title (**Exclude from Kiro…**, **Load only when needed…**, **Run only manually…**; the dots mean a change preview opens first):

- Those three buttons (on one item or on the whole group) build **one** edit with every change and hands it to the editor, which shows its own **change preview**: a diff with a checkbox per change and **Apply** or **Discard**. The editor shows every change **unticked** (it treats them as changes that need confirmation), so tick the ones you want before **Apply**; Bobert says so when the preview opens ("Tick each change you want in the preview, then select Apply. Nothing changes on disk until you save the file."), and **Apply** with nothing ticked ends with "No changes were made. To prepare a change, tick it in the preview, then select Apply." Each change carries a short why and the alternatives (for example: "Kiro may read this file into the agent's context; excluding it keeps requests smaller. Alternative: Hide this item."). Nothing changes until you apply, and even then the edits are only **unsaved**: you review and save them yourself, and Bobert never saves. After applying, a notice says "Changes prepared in M files — review and save." (M is the number of files that now have unsaved changes); if you discard the preview, nothing changes. The preview needs an editor that supports confirmed edits (the standard VS Code change preview); it was observed in native Kiro on macOS with the synthetic demo (2026-10-20), not yet on Windows or Ubuntu. If an editor has no change preview, it applies the changes directly as unsaved edits, and the tick hint does not apply there. Bobert still never saves, so check the unsaved files before saving. "No changes were made." is shown only when the edit was discarded or the editor refused it. When saving `.kiroignore` would have no effect yet (Agent Ignore Files is empty or does not list it), the notice adds "Kiro uses .kiroignore only when it's listed in Agent Ignore Files." with an **Open setting** button. When you save a Steering or Hook file that Bobert prepared, the Steering and Hooks review runs once more by itself (the same checks and limits as the manual review, without taking focus) so the view reflects the saved file; a save while a review is running is answered by one more review when it finishes. Saving an ignore file still re-checks the audit; with the automatic review off, no other save starts the Steering and Hooks review. A hook with two findings (for example a broad trigger and a large prompt) is changed once. Choices of this view: the apply commands are not listed in the Command Palette (they are group and item buttons), file actions are all called **Show file**, every group, the category sub-groups and **Not checked** start collapsed, and Steering and Hook items have no **Hide this item** (it only hides filename findings).
- **Exclude from Kiro** adds root-anchored lines to `.kiroignore`: the edit goes into the opened `.kiroignore`, or into an unsaved new `.kiroignore` if there is none. If your editor saves files automatically (`files.autoSave`), the lines open in a separate new tab instead, for you to copy into `.kiroignore`. The diff-icon button on the group does this for every listed item; **Copy .kiroignore lines** (in the group's right-click menu) copies the lines to the clipboard instead.
- **Hide this item** (the closed-eye icon) hides a filename finding for this workspace. Only salted hashes are stored in the editor's per-workspace storage, never paths. The entry **N hidden by you** (**Show again**) brings them back. This does not exclude the file from Kiro. Steering and Hook items do not have it.
- **Show file** reveals a filename finding in the Explorer without opening it, and opens a Steering, Hook or `AGENTS.md` file in the editor. **Disable hook** (hooks only) is in the item's right-click menu as the alternative to **Run only manually**.
- Guards for the Steering and Hook actions (**Load only when needed**, **Run only manually**, **Disable hook**, **Narrow the pattern**): trusted workspace, the folder checks, a regular file whose real location is inside the checked folder, no hard link, a file unchanged since the check (before and after opening it, and again right before the edit is built), and no edit to a file with unsaved changes or with auto save on (checked per document, so a per-language override counts). In a group an item that fails a guard is skipped and counted ("K items skipped because they changed or are unsaved"); items skipped only because of auto save are counted in a separate fixed text ("K items not changed because your editor saves files automatically. Open the files to edit them yourself."). Guards for **Exclude from Kiro**: trusted workspace and the folder checks, `.kiroignore` must be a regular file (not a symbolic link or folder) or absent, the edit goes into the editor's own `.kiroignore` document, and with auto save on (read per document) the lines open in a separate tab instead.

Suggestions include unclear findings, so review them before saving. "No safe rule could be suggested" appears when a path has unsafe characters or a rule would also match other files. According to Kiro's documentation (not verified by Bobert), for Kiro IDE to use `.kiroignore` it must be listed in `kiroAgent.agentIgnoreFiles`; the view shows ".kiroignore isn't active yet" when a `.kiroignore` exists but is not listed, and opens that setting when you select it. Only this folder's ignore files are checked, not global ones. Excluding files can hide files Kiro needs, so add only what you want excluded.

Reminders and automatic runs: about 30 seconds after Kiro starts, Bobert checks once whether the open workspace (a single trusted local folder) is due. A workspace that was never audited gets one prompt; afterwards you are reminded after `bobert.auditReminderDays` days (default 30, 0 turns reminders off), with **Run audit**, **Later** (7 days) and **Don't remind me**. If you set `bobert.auditAutomatically` to `onOpen` (default `off`; the earlier `true` is still read as `onOpen`), an audit that is at least one UTC day old runs silently with the same limits when the workspace opens, and only notifies you when it finds something; a never-audited workspace still asks first, and reminders off (0), a snooze or **Don't remind me** also stop automatic runs. `onOpenAndChanges` does the same and also watches that single folder for new files or folders matching the audit's own name patterns (not size-only "large files", and nothing inside folders the audit never enters). This happens only in a workspace that was audited before and is not snoozed or set to **Don't remind me**. A few seconds after such files stop appearing (at the latest about a minute into a steady stream), the folder is re-checked silently; if a new file is a secrets finding that was not in the previous result, you get at most one notice per window and UTC day. Name matching for the watcher may be case-sensitive on some systems, so an unusually capitalised file can wait for the next full check. The paths of new files stay in memory until that re-check; nothing new is stored. Both settings apply only from your user settings, so a repository cannot turn automatic runs on or reminders off. Per workspace only the last audit date, a snooze date and a do-not-remind flag are stored. **Bobert: Reset Workspace Audit Reminder** clears the snooze and the flag.

After a workspace has been checked in this window, saving `.kiroignore` (or a file named in Agent Ignore Files) in that folder, or changing `kiroAgent.agentIgnoreFiles`, re-runs the check of that same folder about a second later. The re-check shows no notification; like any completed check it updates the view and the Workspace audit card and records the check date (which postpones the reminder). A prepared, unsaved **Exclude from Kiro** edit is kept. Other saves and settings start nothing, and a folder that has not been checked in this window is never re-checked.

The credit view (**Show Credit Budget**) has a small **Workspace audit** card below the Cost Advisor: it shows the number of items and when the audit ran (or an invitation to run the workspace audit with the last audit date in UTC, or "This folder can't be checked. Run the audit to see why."), with **Run audit** and, once audited, **Show results**. It shows no folder name or path and claims no measured savings. The Cost Advisor section ends with a collapsible **Change your plan answers** form (plan, billing, purchased add-on credits and remaining add-on credits), open by default when the view opens while your plan is unconfirmed (your own open/closed choice is kept while the view is open); the same questions are available from the editor-title button and the status bar item. The **Open Cost Advisor** button appears there only as a fallback while the inline form is not available (for example before the page has loaded or if the live view could not be updated). The view runs one bundled script with a per-load nonce (no network access); its only command links are these five Bobert commands (`bobert.costAdvisor`, `bobert.auditWorkspace`, `bobert.audit.show`, `bobert.share`, `bobert.reportProblem`), enabled through the webview's command allowlist, none with arguments. A quiet footer line also links to rating Bobert on Open VSX, starring it on GitHub and supporting it on Ko-fi (fixed addresses, opened only when you click), plus **Copy share link**, which copies a short fixed text with the Open VSX link to your clipboard, and **Report a problem**, which runs **Bobert: Report a Problem** (see Diagnostics below).

The audit, Copy Diagnostics and the gauge of an earlier development candidate (under the previous name Cyclegauge) were tested by the maintainer in native Kiro on macOS; the audit view wording, the Workspace audit card, the Exclude and hide actions, reminders, the footer links, Share, Report a Problem (including the error-notification button and opening the form), the support prompt, the re-check after ignore changes and the onOpenAndChanges watcher have not yet been verified in native Kiro, the "Kiro not detected" note and status have not been verified in any non-Kiro editor, and no testing of these features on Windows or Ubuntu is recorded. Testing of earlier versions is listed in the [version history](version-history.md).

## Credit view and status bar

The status bar item reads **Kiro credits: On track • 12/day** (the truncated daily budget), **At risk**, **Likely to exceed • runs out 28 Oct**, **Provisional**, **Collecting data**, **Stale data** or **Unavailable**. A warning background means a budget risk (tight or likely to exceed); red appears only once the reported limit is reached or exceeded. Stale or unavailable data shows the warning icon without a colour. If Kiro is too old or the stored data is newer than Bobert, the item says **Kiro: Needs a newer Kiro** or **Kiro: Update Bobert**. The tooltip gives the exact daily budget and observed rate in credits per day.

The credit view shows, in this order: the status (a headline, the credits used, credits left and next reset, and the time of the last account update with its freshness), the usage chart, **Observed usage** (**This cycle vs last cycle** and **Today (UTC)**, shown only when there is something to show), the cycle recap when one is available, the Cost Advisor, the Workspace audit card, **Your Bobert summary** and a collapsed **Advanced details** section (which also holds the CSV export). The caveats that apply to every figure are said once, under **About these numbers** in the status: figures are as of the last account update, the reported limit is not verified as base-only or total capacity, credits above it do not by themselves establish overage charges, forecasts assume the observed pace continues, and dollar amounts are modelled from list prices in USD before tax. When usage is above the reported limit the status shows one headline figure (credits over the limit so far, with the modelled dollar value when a valid price list exists) and one line for the pace until the reset. When there is no usable account update yet, the status says what to do next ("Use Kiro for a few minutes so it can write a credit update. If this stays empty, use Report a problem below.").

## Budget warnings

Inside Kiro, Bobert can tell you early when your reported credits are running low, with a short message and two buttons: **Show details** (opens the credit view, where the price, the price-list date and the caveats are) and **Turn off budget notices** (sets `bobert.budgetWarnings` to off in your user settings; it also ends the right-sizing tip, which has no separate switch). There are three notices that warn about the limit and one that helps you save, all based only on a fresh account update (never on stale data):

- **Forecast**: a regular, current forecast (not a provisional early estimate) says the reported limit is reached before the reset: "At this pace your Kiro credits run out on {date}, {n} days before the reset."
- **Percent**: you have used the configured share of the reported limit (`bobert.budgetWarningPercent`, default 80; 0 turns this notice off): "You have used {p}% of your reported Kiro credits ({used} of {limit}); the reset is in {n} days."
- **Limit**: usage has reached the reported limit: "You have reached the reported Kiro credit limit ({used} of {limit}); the reset is in {n} days."
- **Right-sizing** (lowest priority, only in the last 7 days before the reset): "You will likely leave about {n} credits unused this cycle, and the last cycle also fit within {Smaller plan}. {Smaller plan} would cost about ${x} a month less (modelled)." See below.

Each notice appears at most once per billing cycle (identified by the observed reset time) and at most one notice per window; if several are due at once, only the most severe (limit, then forecast, then percent, then right-sizing) is shown and the others count as handled. The status bar item has a warning background for budget risk (at risk or likely to exceed, a provisional estimate included) and turns red only once the reported limit is reached or exceeded; stale or unavailable data shows just the warning icon with no colour. This colour is part of the gauge and is independent of `bobert.budgetWarnings`. Accounts whose data includes extra credits, which Bobert does not support, get no budget notices. Both settings are user-level only (a workspace cannot change them). The only state kept is the cycle and which notices were shown (see [privacy and storage](privacy-and-storage.md)); nothing is sent anywhere.

When the forecast or the observed usage goes beyond the reported limit, the credit view and the forecast and limit notices add a modelled cost. The credit view shows, for example, "At this pace by the reset: about 200 credits over (≈ $8.00, modelled)", with the price per credit, the price-list version, its review date and the caveats said once under **About these numbers**; the notices stay short and carry only the figure and the word "modelled" ("At this pace your Kiro credits run out on 28 Oct, 3 days before the reset (about $4.80 over the limit, modelled)."), and only after a regular forecast; **Show details** opens the credit view. It is projected credits over the limit times the per-credit price from Bobert's reviewed price list, rounded to whole cents, and shown only when that price list is valid; otherwise only the credits are shown. It is a modelled scenario, not an invoice: whether overage applies depends on your plan and settings, and the reported limit is not verified as base-only or total capacity. Usage already above the limit is the credit view's headline figure ("{n} credits over the limit so far (≈ $x, modelled)"), shown only while the account update is current and left out for accounts with extra credits.
Two plan facts accompany these figures. Both are modelled or list-price information, not advice, and nothing is shown whenever an input is unknown. If your plan is only inferred from the reported limit, the sentences name it ("For comparison, if you are on {Plan}: …" and "If you are on {Plan}: …").

- **Next larger plan** (beside a projected overage): the credit view adds, right after the projected-overage line, "For comparison: {Next plan} costs ${x} a month more than {Current plan} and includes {n} more credits (list prices, price list reviewed {date}).", and the forecast and limit notices that carry an overage cost append the short form "For comparison: {Next plan} costs ${x} a month more and includes {n} more credits." These are only the two differences from Bobert's reviewed price list: no recommendation and no claim that switching would save money. Nothing is shown for Power (no larger plan), when your plan is unknown, for accounts with extra credits, or when the price list is invalid.
- **Plan right-sizing** (read-only on the Cost Advisor's 1-month comparison, so it appears only with a regular forecast and a usable comparison that shows a saving): when the forecast leaves part of your limit unused, a smaller plan would cost less, and the last completed billing cycle also ended within that plan's credits, the credit view shows the sentence above at any time; the notice appears only in the last 7 days before the reset, once per cycle. The size threshold is deliberate: the smaller plan must cover the projected usage, so the unused part is at least the gap between the two plans. "The last cycle fit" means the last cycle's observed usage plus an allowance for its last unobserved hours (the gap from the last observation to the reset at that cycle's average pace). Observed usage is taken from the stored history only where the cycle's start and every step are backed by observations, so this needs three observed billing cycles, and nothing is shown when anything is missing. Unused credits are rounded down. Moving to Free is never suggested. It is a modelled comparison, not advice to change plan: check your real plan, add-on credits and Kiro's terms first.

No plan is ever changed by Bobert.

## Support prompts

Besides the footer in the credit view, Bobert may ask once per window, inside Kiro only, “Finding Bobert useful? Rate it or support development. You can turn these off in Settings › Bobert › Support Prompts.” The buttons are **Rate**, **Support** and **Later**. Rate opens the Open VSX review page; Support opens Ko-fi. Either action snoozes the prompt for 120 days; **Later** or closing the message snoozes it for 60 days. It can appear about one minute after you save an **Exclude from Kiro** edit, once at least one UTC day has passed since first use. Opening **Show Credit Budget** on three distinct UTC days or completing a Cost Advisor review can also trigger it earlier, without a seven-day wait. Opening or cancelling the Advisor, or clearing its answers, does not count. Otherwise, the fallback check is about three minutes after start, at least seven UTC days after first use and only after a forecast or audit finding was shown. A pending saved-exclusion prompt waits its full minute unless a separate medium signal qualifies. Turn it off at any time with the user setting `bobert.supportPrompts` (a workspace cannot change it). Existing users who selected **Don't ask again** remain opted out; **Bobert: Reset Reminders and Saved Summary** (command `bobert.support.reset`, in the Command Palette) clears all saved support dates and flags, including that legacy opt-out, detail-view days and Advisor-used flag. Reset does not allow a second prompt in the same window. Prompt state is only dates (at most three detail-view days) and flags in the editor's global storage. Nothing is sent anywhere; a link opens only when you click it.

Maintainer native test (synthetic profile only): run `BOBERT_SYNTHETIC_SUPPORT_TEST=1 pnpm demo:setup --open --vsix <candidate.vsix>` on macOS/Linux (PowerShell: `$env:BOBERT_SYNTHETIC_SUPPORT_TEST='1'; pnpm demo:setup --open --vsix <candidate.vsix>`). The generated opener supplies a marker matching the demo source; the extension also requires the isolated demo home and global storage. Install the supplied candidate in that demo window, run **Reset Support Prompts**, create an invented `.env` in the demo workspace, run the audit, choose **Exclude from Kiro**, then save as `.kiroignore` in that workspace. The prompt should appear about a minute later. This opt-in only treats first use as yesterday; it preserves the setting, Kiro detection, snoozes, never flag and once-per-window limit. A reload is needed to test another prompt after one has appeared. Without the explicit flag, the demo uses ordinary timing. No native verification of this change is claimed.

In an editor that is not Kiro (and without `bobert.sourceRoot`), when Bobert finds no Kiro logs it shows "Kiro not detected" in the status bar, says the same in the credit view and explains once that it is built for Kiro (with the buttons **Run workspace audit** and **Got it**). If Kiro is installed next to that editor and its logs are found, it works normally and shows no note. The workspace audit still works.

## Diagnostics

Run **Bobert: Copy Diagnostics** (`bobert.copyDiagnostics`) to open the report in an unsaved document and copy it to the clipboard. The extension command writes no file. To report a problem, run **Bobert: Report a Problem** (`bobert.reportProblem`), or choose the **Report a problem** button on one of Bobert's own error notifications or the **Report a problem** link at the bottom of the credit view. It builds the same report, opens it in an unsaved document for review, copies it to the clipboard and then opens Bobert's fixed GitHub bug-report form in your browser, where you can paste the report. Nothing is put in the address and nothing is sent by Bobert. Alternatively run the CLI with `--diagnostics`: it first performs the normal import into Bobert's own store and writes nothing else.

The report contains only fixed codes, counts and platform metadata: Bobert, editor and editor version, Node and Electron versions, platform, architecture, SQLite availability, store state and version, whether storage, source and timezone are default or chosen, status and forecast tier, gauge state, whether the audit is available, counts of snapshots, accounts and unassociated snapshots, a collection result (CLI only), a freshness bracket, import codes and a discovered-log count. It contains no paths, identifiers, amounts or log content. Review it before pasting it into an issue.

## Requirements and command-line tool

Node.js **24.13 or newer**. Runtime uses built-in modules only; TypeScript and Node type definitions are development dependencies. Install development tools with `pnpm install --frozen-lockfile`.

Run from this checkout:

```sh
node --disable-warning=ExperimentalWarning src/cli.ts --source-timezone Europe/Berlin
node --disable-warning=ExperimentalWarning src/cli.ts --source-timezone Europe/Berlin --json
node --disable-warning=ExperimentalWarning src/cli.ts --help
```

Declare the timezone actually used by the source logs. Europe/Berlin is supported by the discovery observation, not a universal default. Offset-free timestamps without a declared IANA timezone are unavailable. DST overlaps and nonexistent wall times are rejected rather than guessed. Offset-aware timestamps preserve their spelling and normalize their instant to UTC.

Options:

| Option | Purpose |
| --- | --- |
| `--source-root <directory>` | Override the Kiro IDE data root, containing `logs/` |
| `--source-timezone <IANA>` | Interpret offset-free source timestamps |
| `--store-dir <directory>` | Dedicated private app-owned directory outside the source `logs/` and Git repositories |
| `--max-age-hours <hours>` | Observation freshness threshold, default 24; operational policy, not measured service latency |
| `--diagnostics` | Print the diagnostics report (fixed codes and counts); first performs the normal import into Bobert's own store |
| `--json` | Local billing/quality query output without account, source or deduplication keys |

Default source candidates: macOS `~/Library/Application Support/Kiro`; Windows `%APPDATA%\Kiro`; Linux `${XDG_CONFIG_HOME:-~/.config}/Kiro`. Only `logs/<run>/<window>/exthost/kiro.kiroAgent/q-client.log` and numeric suffixes such as `q-client.log.1` are read. These suffixes are an explicitly supported synthetic rotation convention, not a verified Kiro rotation contract.

Default owned storage. **Extension:** the editor's own per-extension storage folder, `User/globalStorage/stefansuess.bobert` beneath the editor's data root, like other extensions (on macOS `~/Library/Application Support/Kiro/User/globalStorage/stefansuess.bobert`). **CLI** (no editor available): macOS `~/Library/Application Support/Bobert`; Linux `${XDG_DATA_HOME:-~/.local/share}/Bobert`; Windows `%LOCALAPPDATA%\Bobert`. The two defaults differ, so pass `--store-dir` to query the extension's store from the CLI. On POSIX, storage must have owner-only access. A chosen location must be outside the source root. On Windows the defaults rely on the user profile's permissions only when the editor's data folder is inside the user profile (a portable install or a custom `--user-data-dir` on a shared drive is not protected), and a chosen location is verified (see [platform verification](platform-verification.md)). The source `logs/` folder, anything containing the source root, Git repositories, symlink paths and `kiro-cli`/`.kiro` directories are rejected as store locations. On macOS, use canonical paths when a path includes system aliases such as `/tmp` or `/var`.

The CLI prints observed usage, reported limit, remaining reported credits, reset UTC instant, as-of time, quality flags and fixed import diagnostic codes. A successful query exits 0 even when values are unavailable; configuration, storage or fatal collection failures exit 1 with a fixed code. JSON output follows the same policy.

## Troubleshooting

- **"Collecting data" for a long time.** The extension only reads usage that Kiro has already written to its logs. Wait for the next scan, which runs every minute and when log files change. A forecast additionally needs several observations over days; see [forecasting.md](forecasting.md).
- **"Unavailable".** The logs could not be read or have an unsupported format, the storage location is not safe (for example on Windows a chosen storage location that cannot be verified is refused, or a path containing a symlink), or several accounts were detected. No numbers are invented in these cases.
- **Settings changes do not apply.** `bobert.sourceRoot`, `bobert.storageRoot` and `bobert.sourceTimezone` are read when the extension activates. Reload the window after changing them.
- **"Kiro: Needs a newer Kiro" or "Kiro: Update Bobert".** The first means the runtime has no SQLite support, the second that the stored data was written by a newer Bobert. Update Kiro or Bobert respectively; stored data is never modified. **Bobert: Copy Diagnostics** shows which case applies.
- **Node.js.** Node.js 24.13+ is required to build and for the CLI. The installed extension runs inside Kiro's own extension host; which Node features that host provides has only been observed on Kiro 1.2.56 (macOS), and no minimum Kiro version is established.
- **Remote or SSH workspaces.** Not verified. The extension is declared as a UI extension that reads local files.
- **Removing local data.** Delete the storage folder listed under "Default owned storage" above. Kiro's own files are never touched.
