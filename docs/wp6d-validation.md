# WP6d results summary validation

Phase 6d adds the static section "Your Cyclegauge summary" to the credit view and the one new persisted key `cyclegauge.results.v1`. Phase 6e (recap, CSV, image) is not part of it.

What it does. A saved Exclude edit that matches the prepared one adds an aggregate of the accepted findings (item count, possible secrets, total size with a lower-bound flag when any size is unknown) under the observed billing cycle, the latest billing reset that is still in the future. Without an observed cycle nothing is counted. The key holds at most two cycles, `{ cycle, bytes, bytesLowerBound, items, secrets }[]`, in global state only, not registered for Settings Sync, with no path, name or identifier. A value of any other shape reads as unknown, is never overwritten and is cleared by the explicit Reset Reminders and Saved Summary command. The section labels the figures "exclusions you saved", says it covers at most the current and previous cycle, and shows sizes of unwalked folders as "at least" or "size unknown", never zero. The observed use trend compares exact per-observed-day net change over the last 28 days with the 28 days before, from `history().evidence.intervals` only. Each window needs 70 % of its time covered by whole intervals (edge-straddling intervals are left out, not prorated); exclusions or a stop other than the 85-day range give "not comparable". It is worded as an observation with the cause open; there is no plan-change line and no saved-credits figure.

Verification in the implementation worktree: `pnpm typecheck`, `pnpm test`, `pnpm test:release`, `git diff --check`. Unit tests (`tests/unit/results-summary.test.ts`) cover the strict validator with hostile, prototype-key, getter, extra-key, newer-shape and oversize values, record and pruning, saturation, the finding aggregate, every not-observed and not-comparable trend case, the 70 % boundary to the hour, exact decimals, and the rendered section (heading, labels, escaping, no script and no `style=`). Packaged-bundle tests (`tests/release/advisor-bundle.test.ts`) show that a matching save records once, another file or a replayed save records nothing, an unreadable value is left as it is, nothing is counted without an observed cycle, and the reset clears the key.

Open: native Kiro acceptance of the section in the live dashboard (keyboard and screen-reader reading order), behaviour with a real prepared edit on macOS, Windows and Ubuntu, and the mandatory independent `security-reviewer` review of the persisted key before merge. A reset between a save and the next render updates the view at the next refresh.

Known limitation: two windows saving close together can each overwrite the other's addition, so totals may come out low (approximate counting). The reset command is shared with the support prompts and is titled accordingly.
