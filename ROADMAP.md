# Cyclegauge roadmap

Current release: **0.7.0** beta (macOS, Windows, Ubuntu), still the last published release (checked 2026-10-18; no 0.9.0 or later has been published). Merged on `main` and unreleased: the workspace audit (WP1a–i), storage ladder, runtime guard and diagnostics (WP2a–d), the interactive dashboard with results summary, cycle recap and CSV export (WP6a–e), budget warning and overage cost (WP7, WP8), plan right-sizing hint (WP8b), first-minute walkthrough (WP15) and session hints (WP11, WP13), the first three parts of the Hook and Steering review (WP10a–c) and the stable release channel (WP5a, #122). In progress: WP10d (opt-in automatic review). Next: a single 0.13.0 beta (0.9.0 and 0.11.0 are skipped, decision of 2026-10-18), then 1.0.0 stable; see [path to 1.0](docs/path-to-1.0.md). Milestones 0–3, 4A, 4B, 4C (0.4.1), 5 (0.5.0 usage chart) and 6 (0.7.0) are implemented; synthetic and local UI evidence is recorded in the per-milestone validation documents. Remaining work (session aggregation, Crew integration, Kiro SQLite access, usage-efficiency insights) is deferred and unauthorized. Sections labeled “approval” or “boundary” below are dated historical records and are superseded by later approvals where stated.

## Path to 1.0 — scope decision (approved 2026-10-17)

The maintainer approved the value-first plan in [path to 1.0](docs/path-to-1.0.md) (WP0). 1.0.0 is the first stable release and the first public announcement. Its scope is the current features plus the user-triggered workspace/ignore audit from #71 Capability A, on macOS, Windows and Ubuntu; RHEL and macOS Intel stay unsupported for 1.0. The audit has a time limit of about four weeks to a 0.9.0 beta tested by invited users; if it is not solid by the end of the beta, 1.0 ships without it. #71 Capabilities B–D are post-1.0.

Audit boundary: the audit runs only when the user invokes its command. It may enumerate bounded file metadata (relative path, type, size) under one chosen trusted local root, and may read only workspace ignore files (`.kiroignore` and the files named by the `kiroAgent.agentIgnoreFiles` setting) plus that setting's value. It reads no other file contents, follows no symlinks or junctions, writes nothing, persists nothing and sends nothing. Each work package still lands as its own reviewed PR; this decision does not approve merges, releases or outreach.

Audit boundary update (approved 2026-10-17 after native testing of the 0.9.0 candidate; 0.9.0 stays unpublished and is extended): findings move to a native sidebar list with per-finding **Accept**, **Ignore** and **Show file**. *Accept* prepares the `.kiroignore` change as an unsaved edit (or an unsaved new file) that the user reviews and saves; Cyclegauge writes no workspace or settings file itself, and adding `.kiroignore` to Agent Ignore Files is offered by opening the setting. *Ignore* hides a finding for that workspace; only salted SHA-256 hashes of category and relative path are kept in the editor's per-workspace storage, never paths. A reminder appears when a workspace has not been audited for a configurable number of days (default 30, 0 = off); per workspace only the date of the last audit, a snooze date and a do-not-remind flag are stored. An opt-in setting (default off) may re-run the audit automatically when it is due, in a trusted workspace only and with the same read limits. Both settings are user-level only (`application` scope), so a repository's own settings cannot enable automatic runs or turn reminders off.

Audit UX update (approved 2026-10-17 after native testing of the sidebar): plain-language wording in the audit view ("Kiro may read this", "Exclude from Kiro", "Not a problem"), a summary line, a short reason per category and a positive empty state. The credit detail view gains a small workspace-check card (findings count and last check date for the open workspace, no paths). For its buttons the detail view enables command links for exactly three Cyclegauge commands (`cyclegauge.costAdvisor`, `cyclegauge.auditWorkspace` and `cyclegauge.audit.show`) through the webview's command allowlist; scripts stay disabled and no other command can be invoked from the view. An interactive dashboard with scripts (chart hovers, an inline Cost Advisor form) is a candidate for 1.1 and needs its own design and security review (nonce CSP, validated message protocol, accessibility).

Community prompts (approved 2026-10-17; overrides the no-pop-up stance in #74): getting the word out matters more than never prompting, but every prompt must be easy to turn off. The credit detail view gets a quiet footer with fixed links to rate on Open VSX, star on GitHub and support on Ko-fi, plus a *Share* link that runs `cyclegauge.share`, which copies a fixed text with the Open VSX link; the webview command allowlist is therefore exactly four commands (`cyclegauge.costAdvisor`, `cyclegauge.auditWorkspace`, `cyclegauge.audit.show`, `cyclegauge.share`), scripts stay disabled. A support prompt may appear inside Kiro at most once per window, no earlier than 7 days after first use and only after the user has seen a forecast or an audit finding; any rate/star/support choice snoozes it for 120 days, *Not now* or dismissal for 60 days, and *Don't ask again* stops it. The user-level setting `cyclegauge.supportPrompts` (default on, `application` scope) turns it off. Outside Kiro, a one-time notice explains that Cyclegauge is built for Kiro and the status bar shows "Kiro not detected" instead of collecting. Prompt state lives only in the editor's global state (dates and flags, no user data). No telemetry, no tracking parameters and no network access except links the user clicks.

Community prompt timing update (WP1h, approved 2026-10-17): this supersedes the timing rule above. A saved edit prepared by **Exclude from Kiro** permits a prompt about one minute after the save, at least one UTC day after first use. Opening the credit detail view on three distinct UTC days or completing a Cost Advisor review permits an earlier prompt without a seven-day wait. The seven-day plus forecast/finding-seen rule remains the fallback. Keep Kiro-only, once per window, user-level opt-out, 60/120-day snoozes, never flag and fail-closed write-before-show. Only bounded local dates, counters and flags are stored; no paths, content or telemetry. An explicitly enabled isolated synthetic demo may override first-use age for native testing; ordinary usage cannot.

Community prompt UI update (approved 2026-10-17): this supersedes the button and message descriptions above while preserving the approved timing and privacy rules. Use the message “Finding Cyclegauge useful? Rate it or support development. Turn off reminders in Cyclegauge settings.” with exactly **Rate**, **Support** and **Later**. Rate opens the existing Open VSX review link; Support opens the existing Ko-fi link. Either action snoozes for 120 days; Later or dismissal snoozes for 60 days. Remove the GitHub Star and **Don't ask again** buttons. Keep the existing legacy never flag as a suppression gate and keep reset compatibility so previous opt-outs remain honored until users explicitly reset support prompts. The user setting and footer links remain as documented; no timing, persistence, collection, dependency or setting changes are approved.

Audit triggers and patterns (approved 2026-10-17; supersedes "runs only when the user invokes its command" for the cases below, all other audit boundaries unchanged): checks are event-driven, never timer-based. **(1)** After a workspace has been checked, saving `.kiroignore` or a file named by `kiroAgent.agentIgnoreFiles`, or changing that setting, re-runs the audit for that workspace so the view and the detail card are not stale; this applies to everyone because it only refreshes a result the user asked for. **(2)** `cyclegauge.auditAutomatically` becomes `off | onOpen | onOpenAndChanges` (default `off`; the existing boolean `true` maps to `onOpen`). `onOpen` re-runs an audit older than one UTC day when a trusted workspace opens. `onOpenAndChanges` adds a file watcher limited to the audit's own name patterns (never the whole tree, never pruned folders), debounced, that re-runs the audit when a matching file appears; results update the view and card silently, with at most one notification per workspace per UTC day and only for new **Secrets and credentials** findings. Watcher events stay in memory; nothing new is persisted beyond the existing dates and flags. Native watcher behaviour must be verified per platform before support is claimed. **(3)** The name patterns are extended from a curated list informed by public name-based lists (eth0izzle/shhgit, MIT; github-linguist/linguist `vendor.yml`, MIT; github/gitignore, CC0), written as our own patterns with a synthetic test per pattern; nothing is imported wholesale, and content-based scanners are out of scope because the audit never reads file contents. The concrete additions need maintainer review of the gap list before implementation. Point 1 lands as its own PR; points 2 and 3 form a separate work package.

1.0 killer features (approved 2026-10-17; supersedes "Not in 1.0: Hook/Steering analysis" and moves #71 B into 1.0): 1.0 is a feature-complete vertical slice with a "wow" factor; not everything has to be perfect. Its scope adds a budget warning before credits run out (WP7), an overage cost projection in dollars from the reviewed pricing catalog with an upgrade-vs-overage comparison, labelled as a modelled scenario (WP8), a plan right-sizing hint after two cycles with many unused credits (WP8b), a results summary built only from known facts, with no estimated "saved credits" figure (WP12), a shareable cycle recap card rendered locally without identifiers (WP14), a first-minute walkthrough (WP15), the audit's total exposed size (WP1i), a previous-cycle comparison and today's pace in the dashboard (WP6), and a Hook and Steering review (WP10, #71 B plus the Steering part of #71 A). A context/message reminder (WP11) is included only if a data proof shows that Kiro's local data exposes message counts or context fill with clear semantics; otherwise it moves to 1.1 by documented decision; the same applies to a model choice hint (WP13), which needs a documented model setting and published per-model credit multipliers. Release sequence: 0.9.0 beta → 0.11.0 beta (WP6, WP7, WP8, WP8b, WP1i, WP12, WP14, WP15) → 0.13.0 beta, the last feature beta (WP10, WP11, WP13) → 1.0.0 stable with no further features. Listing and launch copy leads with value; privacy and security are a baseline, not a selling point. This decision sets scope only: each WP still needs its implementation go-ahead; WP6 and WP10 need their own design approval first, and WP10's read of Kiro configuration text and WP11's session-data access need explicit approval under AGENTS.md. Session attribution (#71 C) and analysis of prompt or conversation content stay out of 1.0.

Release sequence update (approved 2026-10-18; supersedes the release sequence in "1.0 killer features" above and every 0.9.0/0.11.0 beta step in [path to 1.0](docs/path-to-1.0.md)): 0.9.0 and 0.11.0 are skipped and never published, because everything planned for them is already merged on `main`. After WP10d lands, **0.13.0** is the single beta and the only build given to invited testers; it carries everything planned for 0.9.0, 0.11.0 and 0.13.0. Then 1.0.0 stable with no further features. The exit criteria change accordingly: the features planned for 0.9.x and 0.11.x must ship in 0.13.x; the invited-tester evaluation of the workspace audit (keep, simplify or drop) happens in the 0.13.x beta; the upgrade test covers 0.7.x, the only published predecessor; the 14-day 0.13.x beta without an open crash or data-loss bug is unchanged. The audit's four-week time limit is measured to the 0.13.0 beta. This decision does not approve publishing 0.13.0, outreach, tags or releases; the maintainer runs the release workflow.

Report a problem (approved 2026-10-18 by the maintainer for 1.0; no telemetry): a command **Cyclegauge: Report a Problem** (`cyclegauge.reportProblem`) builds the existing Copy Diagnostics text (fixed codes, counts and versions only), opens it as an unsaved document for review, copies it and then opens the fixed GitHub bug-report form `https://github.com/StefanSuess/Cyclegauge/issues/new?template=bug_report.yml` in the browser. No diagnostics, identifiers or other data are put in the URL, nothing is sent by Cyclegauge and nothing new is persisted. Entry points: the command palette, a **Report a problem** button on Cyclegauge's own error notifications, and a footer link in the credit detail view, so the webview command allowlist becomes exactly five commands (`cyclegauge.costAdvisor`, `cyclegauge.auditWorkspace`, `cyclegauge.audit.show`, `cyclegauge.share`, `cyclegauge.reportProblem`); scripts, CSP and the message protocol are otherwise unchanged. Telemetry stays out of 1.0.

Session hints on Windows and Linux (approved 2026-10-18): the maintainer decided that the session hints (context reminder and model hint, setting `cyclegauge.sessionHints`) are also enabled on Windows and Linux, not only on macOS. Nothing else about the approved read changes: the same allowlisted fields, read-only handles, bounds, no persistence, local extension host only, Kiro only. Only macOS has observed evidence ([data proof](docs/wp11-13-data-proof.md)); on Windows and Linux the session folder and the path format are unverified, so the feature must fail closed silently with fixed codes (`no_root`, `no_match`) when the layout differs, and native verification on both platforms stays open. This is not approval for session aggregation or any other new read.

Steering review with the audit (approved 2026-10-18): the maintainer decided that a manual workspace audit also runs the Steering and Hooks review, and that the review keeps its own button. A manual audit means every user-initiated run (**Cyclegauge: Audit Kiro Workspace**, the Audit view title button, the dashboard card's **Check now** link, **Run audit** in the reminder, and the credit view's Show / `cyclegauge.audit.show` when there is no result yet, which runs the audit); it then also runs exactly what **Cyclegauge: Review Kiro Steering and Hooks** (`cyclegauge.reviewKiroConfig`) runs, with the same trust and folder guards, the same bounded reads and manual-run semantics (it wins over an automatic run, does not count toward its cap, and the one-time enable offer behaves as after a manual review). Silent audit re-runs (reminder-driven, `onOpen` and `onOpenAndChanges`, the ignore-file re-check) never start the review; `cyclegauge.configReviewAutomatically` stays its only automatic trigger. If the user dismisses the multi-root folder picker or cancels the running audit, no review starts; after an audit failure or refusal (untrusted workspace, refused folder) the review still starts and shows its own refusal. A failure or refusal of one never blocks or hides the other's result. The Audit view title bar gets a button for the review command. This supersedes the WP10 design's "the review is a separate command from the audit" for manual runs only; nothing new is read beyond the review's existing allowlist.

Apply Steering and Hooks suggestions (approved 2026-10-18; supersedes the [Hook and Steering design](docs/wp10-hook-steering-design.md) wording "suggestions as a reviewable preview, never written automatically" and its "preview-only in v1"): findings in the Steering and Hooks review get **apply actions** instead of an untitled plain-text preview. Each prepares an **unsaved edit in the real file**, exactly like **Exclude from Kiro**: Cyclegauge still writes nothing itself and the user reviews and saves. A large always-included Steering file (no front matter, or `inclusion: always`) gets **Load only when needed** (front matter `inclusion: manual` inserted at the start, or the existing `inclusion` value replaced); a Steering file whose `fileMatch` pattern matches every file gets **Narrow the pattern** (the pattern value is selected for the user to type over; no value is generated); an agent hook finding gets **Run only manually** (that entry's `trigger` becomes `"Manual"`) and **Disable** (`"enabled": false`); a large `AGENTS.md` gets **Open file** only. The edit is a minimal text change computed from bytes the review is already allowed to read (the Steering prefix of at most 2 KiB, or the Hook JSON of at most 64 KiB); if the exact place cannot be determined safely (duplicate or escaped keys, unusual formatting) the file is opened without an edit and a fixed message says so; the whole file is never rewritten. Guards: trusted workspace only; the same folder guards as the audit; the file must be a regular file whose real location is inside the checked root; and it must be unchanged since the review (size, modification time and a digest of the bytes the review read, checked again after the editor loaded it), otherwise the user is asked to run the review again; an unsaved or auto-saved document is never edited. Nothing else is read or kept: no file text beyond the approved prefix or Hook JSON, no new persistence, no new setting, fixed messages only (unexpected failures use the **Report a problem** button). Findings that span several files or hooks (combined size, overlapping hooks) keep a read-only **Show suggestion**.

## Milestone 1 — Read-only account snapshot collector and local persistence

Implementation authorized and delivered as a TypeScript/Node.js CLI. Starts with the observed `q-client.log` account-response format; support the cached snapshot only after its database read safety is proven. Do not require session parsing to obtain current account usage.

Deliverables:

- Platform-aware source discovery and explicit root override; no Kiro commands, credentials, authenticated requests, or changes to Kiro settings.
- Allowlisted `CREDIT` snapshot extraction with decimal preservation, reset timestamp, source as-of time, reduced-precision/unsupported status, and safe account partitioning.
- A Cyclegauge-owned SQLite store for normalized snapshots, import cursors, deduplication, and quality evidence. No raw logs, sessions, identifiers, or private paths persisted.
- Restart-safe ingestion with rotation/truncation detection, partial-record handling, freshness, conflicts, and out-of-order observations. Persist gaps as unknown.
- A local query/export contract containing billing fields and quality only; no application UI or forecast required for this milestone.

Acceptance:

- Synthetic tests cover repeated imports/restarts, two account partitions, stale cache rereads, conflicting snapshots, unknown fields/resources, parse failures, precision fallback, same-cycle adjustments, and cycle changes across gaps.
- Filesystem tests demonstrate zero writes to source files and directories, including SQLite sidecars; use generated test data, never production sessions in CI. If safe database access is unavailable, logs still work and cache status explains the limitation.
- Persistence writes only to the app-owned location and emits no private diagnostics, including on failures.
- Snapshot interval differences are never presented as known daily consumption. Cross-cycle counters are not subtracted.
- Validate on macOS first. Windows, Ubuntu, and RHEL remain explicitly unsupported/unverified until their platform acceptance checks in ARCHITECTURE.md pass on actual hosts or appropriate environments. Do not mark one Linux distribution verified from another's results.

## Milestone 2 — Kiro IDE extension

- Reuse the log-only account collector and app-owned store inside a VS Code-compatible Kiro extension.
- Show remaining base credits in the status bar and open a local detail view on click.
- Import at activation; observe log changes and poll as a fallback without making old observations fresh.
- Test activation, refresh, stale status and detail rendering with invented fixtures; package and validate a VSIX in the locally installed Kiro IDE.
- Verify actual extension-host Node and `node:sqlite` behavior. Do not claim Windows, Ubuntu or RHEL support from macOS validation.

Local acceptance: VSIX 0.2.0 was installed through Kiro 1.2.56 on macOS. In a clean IDE window the status bar showed remaining base credits and its click opened the account details, including reset, allocation, original snapshot time, freshness and timezone-assumption warning. This confirms functional extension-host SQLite on this installation. Watcher-triggered updates were tested with synthetic files; live notification reliability remains covered by the polling fallback.
